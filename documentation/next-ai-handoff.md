# 開発を再開するときの確認事項

この文書は、作業を再開するときの参照先と、継続して守る合意をまとめる。担当・作業範囲は現在の依頼で確認し、過去の引き継ぎやレビュー記録だけを根拠に別の作業を始めない。

## 作業前に確認すること

- 製品の実装先は [jphacks/tkb_2616](https://github.com/jphacks/tkb_2616)、仕様の参照先は [Umi-s-Atelie/hobby-platform](https://github.com/Umi-s-Atelie/hobby-platform)。仕様を実装済みの根拠にせず、製品側のコードで確認する。
- 製品リポジトリのルートで `git status --short --branch` と差分を確認する。未コミットの変更を保持し、問題なく更新できる状態で `git pull --ff-only` を行う。競合を解消するために他の変更を reset やファイル全体の置換で消さない。
- pushする場合も、直前にリモートと差分を確認する。force pushで他の変更を上書きしない。
- 個人PCの配置・ブランチ・認証状態・実行権限を固定の前提にしない。秘密値を含むファイルを丸ごと出力せず、値をチャット・Git・ログに載せない。

## 構成と実行

- [src/app/index.tsx](../src/app/index.tsx)が、共有フロントの[app/App.tsx](../app/App.tsx)へ接続先に応じた画面を渡す。ルーティングの使い分けは [app/AGENTS.md](../app/AGENTS.md)を参照する。
- [metro.config.cjs](../metro.config.cjs)はReactの参照をルートに統一し、サーバー用の環境変数ファイル・SQL・Edge実装を配信対象から除外する。
- 認証側の型検査は [tsconfig.auth.json](../tsconfig.auth.json)、フロント側は [app/tsconfig.json](../app/tsconfig.json)を使う。型エラーを避けるために検査を弱めない。

次のコマンドは製品リポジトリのルートで実行する。

```sh
npm run setup          # 依存導入が必要な場合
npm run web            # 開発サーバー
npm run check          # 型検査・テスト・Edge型検査・Web出力
npm run build:native   # iOS/Androidのバンドル確認が必要な場合
npm run doctor:config  # 接続設定を確認する場合
```

`doctor:config`は不足項目名を表示し、未設定なら失敗する。設定値をチャットに貼らない。ルートのWeb出力先は `dist/`。`npm --prefix app run build:web` はモック公開用の `docs/` を再生成するため、検証だけなら出力先を一時フォルダへ指定する。

## データと環境を扱うとき

- 依頼者個人のSupabaseは使用しない。接続・設定・DB適用はチームが指定した環境だけで行い、個人プロジェクトの一覧取得や別用途のプロジェクトの流用もしない。
- 既存のマイグレーション・seed・DB型・業務処理を尊重し、データを初期化しない。適用先と適用済み履歴を確認し、追加SQLの適用状況を推測しない。
- ローカルDBのポートなどは [supabase/config.toml](../supabase/config.toml)を確認する。過去の設定へ戻さない。
- 仕様の承認を契機にAIが自動実装する仕組みは追加・復活させない。現在の依頼に沿って進める。
- 追加のAIや別チャットへの連絡は、ユーザーの許可なしに行わない。

## 画面実装で守る合意

以下は既存の合意であり、実装済みであることを示す一覧ではない。変更するときは現在の依頼と承認済み仕様を照合する。

- DMは設けない。恋愛目的のマッチングアプリとは異なり、ゲーム・趣味を一緒に楽しむ仲間探しに特化。READMEにも反映済み。
- 参加は募集者の **承認制**。「今回は見送る」は後から撤回されたため追加しない。一度承認した相手を募集者が拒否する機能を作らない。
- 募集人数は募集者を除く人数。公開後のゲーム変更は不可。募集編集・開催中止は可能。
- プロフィールへの反映は本人が「プロフィールにも保存」を選んだときのみ。
- 日時・機種・モード・VC変更は成立済み相手へ通知して参加再確認。「参加できない」は辞退で枠を空ける。未回答は成立・枠を維持する。
- 回答期限は変更後の開始時刻。日時未定なら期限なし、確定時に通知。期限超過でも自動辞退せず募集者に未回答・期限超過を表示する。
- 期限内の満員による自動終了は空きが出れば再開。増員による追加受付は開始後も可能。遊び終了・開催中止後は再開しない。受付状態の詳細は最新仕様を確認。
- 通常の新規応募・承認は開始時刻まで。開始時刻に既存成立者の合流情報は消さない。部屋番号と招待URLを両方登録でき、終了・中止までは追加・変更可能。
- 募集者が「遊び終える」、または開催中止で、双方の部屋番号・招待URL・ゲーム内IDを非表示にする。「遊んでいる最中」の状態もある。
- 合流通知は最新の合流画面を開く。通知本文へ秘密の番号・URL・IDを埋め込まない。
- Steamは連携直後・24時間ごとに自動更新。失敗後は初回失敗から1分・5分・30分・2時間、その後5時間ごと。成功で通常周期へ戻る。
- 最終成功日時を表示し、7日超なら「7日以上前」。古いという理由だけで測定値を消さない。取得失敗・非公開を0時間として保存しない。非公開確認時と一時通信失敗を区別する。
- Steam連携解除で取得データを削除し、本人の手入力・募集・成立記録は残す。
- PL/pgSQLは現構成のまま使うことでユーザー了承済み。TypeScriptへ全面置換しない。

## 確認結果の報告

- コードで確認した内容、端末内のデモ、実ユーザー間の処理、実サービスで確認した内容を分ける。未確認のものは未確認と伝える。
- PGliteの検証を、実SupabaseのAuth・Realtimeの疎通確認と同一視しない。バンドル出力の成功を、署名済みアプリの実機確認や実OAuthの成功として扱わない。
- 変更したファイル、実際に行った検証、未確認事項、push・mergeの状態を簡潔に報告する。
